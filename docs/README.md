# Documentation index

The repository README is at [../README.md](../README.md); the platform-neutral skill contract is at [../skills/sentinel-bounty/SKILL.md](../skills/sentinel-bounty/SKILL.md).

## Finding pipeline (phases 5–7, fixtures only)

- [detection-stub-v1](detection-stub-v1.md) — Fixture-only detector stub that reshapes local JSON fixtures into normalized findings (no real scanner); for implementers of the finding pipeline.
- [detector-interface-v1](detector-interface-v1.md) — Pluggable detector interface (synchronous detector contract, built-in stub as reference implementation, safe loader for custom modules, `sentinel detect` CLI); for implementers and reviewers of finding detection.
- [detection-secret-scan-v1](detection-secret-scan-v1.md) — First real detector: `secret-scan` scans operator-supplied local text for well-known credential formats (AWS access key IDs, GitHub and Slack tokens, private-key PEM headers), one finding per distinct secret, never the full secret itself, confidence `potential` (no liveness check); for implementers and reviewers of finding detection.
- [detection-dangerous-call-v1](detection-dangerous-call-v1.md) — Second real detector: `dangerous-call` scans operator-supplied local text for risky code-sink calls (eval, Function, command execution, innerHTML, document.write, unsafe deserialization), one finding per distinct call site, never executing the code, confidence `potential` (no reachability/taint proof); for implementers and reviewers of finding detection.
- [detection-insecure-crypto-v1](detection-insecure-crypto-v1.md) — Third real detector: `insecure-crypto` scans operator-supplied local text for weak-cryptography call sites (MD5/SHA-1 hashes, ECB mode, DES/RC4 ciphers, Node's deprecated createCipher()/createDecipher(), Math.random()/random.random()), one finding per distinct call site, never executing the code, confidence `potential` (no sensitivity/context proof); for implementers and reviewers of finding detection.
- [detection-hardcoded-credential-v1](detection-hardcoded-credential-v1.md) — Fourth real detector: `hardcoded-credential` scans operator-supplied local text for credential-named variables assigned a quoted string literal (password, API key, secret/token), one finding per distinct assignment site, carrying only the masked assignment (`<name><operator> "****"`), never the literal value itself, confidence `potential` (no liveness/use proof); for implementers and reviewers of finding detection.
- [detection-insecure-transport-v1](detection-insecure-transport-v1.md) — Fifth real detector: `insecure-transport` scans operator-supplied local text for cleartext HTTP URLs (host only, never path/query/userinfo; loopback never matches) and disabled TLS verification, one finding per distinct call site, never executing the code, confidence `potential` (no sensitivity/context proof); for implementers and reviewers of finding detection.
- [detection-tainted-deserialize-v1](detection-tainted-deserialize-v1.md) — Sixth real detector, first parser-based: `tainted-deserialize` parses operator-supplied JavaScript (hand-written stdlib-only subset parser) and tracks taint from function parameters and `process.argv` to unsafe deserialization sinks (yaml.load, YAML.load, yaml.loadAll, unserialize), reporting a sink call only when its first argument is tainted or the call is reached through an alias, never carrying a literal value or source line, confidence `potential` (no reachability/taint proof beyond the tracked flow); for implementers and reviewers of finding detection.
- [detection-tainted-command-execution-v1](detection-tainted-command-execution-v1.md) — Seventh real detector, second parser-based: `tainted-command-execution` reuses the same taint engine on command-execution sinks (child_process.exec, execSync, spawn, spawnSync, execFile, execFileSync), reporting a sink call only when its first argument is tainted or the call is reached through an alias, never carrying a literal value or source line, confidence `potential` (no reachability/taint proof beyond the tracked flow); for implementers and reviewers of finding detection.
- [parser-taint-scope-v1](parser-taint-scope-v1.md) — Parser/taint scope v1 (round 95): what regex cannot do and why (code vs prose, aliased calls, taint, cross-function flow), the stdlib-only JavaScript subset parser plus intra-procedural taint approach, the Acorn dependency decision (evaluated, not adopted — vendored Acorn is the upgrade path), and the deliberate limits (JavaScript only, intra-procedural, no sanitizer modeling, no import resolution); for implementers and reviewers of finding detection.
- [detection-policy-v1](detection-policy-v1.md) — Detection policy v1 (round 90): the detector set is complete for the synchronous regex approach (SQL/template/LDAP/XPath need a parser; path traversal/SSRF/open redirect/XXE/ReDoS need taint; key management/certificate validation/password-storage are outside call-site reach), detection does NOT auto-run, detectors are NOT async; for implementers and reviewers of finding detection.
- [validation-v1](validation-v1.md) — Rule-based finding validator with deduplication and an evidence checklist; for implementers and reviewers of finding validation.
- [semantic-dedup-v1](semantic-dedup-v1.md) — Conservative semantic dedup v1 (second pass after exact-key dedup: same type + asset + base vector/severity band + shared evidence entry; merged finding keeps the evidence union, highest score, and `merged_from`; fuzzy matching out of scope, open policy question); for implementers and reviewers of finding validation.
- [ai-verdict-v1](ai-verdict-v1.md) — Pluggable AI-verdict interface (synchronous verifier contract, built-in stub that always answers needs_evidence, safe loader for custom modules, advisory-only precedence); for implementers and reviewers of finding validation.
- [policies-f6-v1](policies-f6-v1.md) — Phase 6 policies v1 (round 90): semantic dedup is conservative, rule-verdict false positives are excluded from reports (opt back in with `--include-false-positives`), AI verdicts are advisory-only and never override the rule verdict, detectors are NOT auto-run and NOT async; for implementers and reviewers of finding validation.
- [policy-versioning-v1](policy-versioning-v1.md) — Policy versioning v1 (round 96): `POLICY_VERSION` tracks the decision set (MAJOR = a decision changed, needs a user decision; MINOR/PATCH = enforcement or doc changes, no bump), current version 1.0.0, how the operator checks the active version (`sentinel policy`, stderr notes), the v1-to-v2 migration procedure, and compatibility rules; for implementers and reviewers of finding validation.
- [evidence-checklists-v1](evidence-checklists-v1.md) — Per-class evidence checklists (8 classes in `knowledge/evidence-checklists.json`, runtime-loaded, generic fallback): which evidence each class must carry, how classes are matched, and the generator rendering; for implementers and reviewers of finding validation.
- [cvss-vector-v1](cvss-vector-v1.md) — CVSS 3.1 base-vector parsing and scoring (parser, formulas, vector-vs-score precedence, known limitations); for implementers and reviewers of scoring.
- [cvss-temporal-environmental-v1](cvss-temporal-environmental-v1.md) — CVSS 3.1 temporal (E, RL, RC) and environmental (CR, IR, AR, MAV, MAC, MPR, MUI, MS, MC, MI, MA) metrics: parser extensions, formulas, precedence rules, and the no-offline-oracle limitation; for implementers and reviewers of scoring.
- [pipeline-v1](pipeline-v1.md) — End-to-end lab-local pipeline (stub detector → validator → dedup → report generator) over fixtures; for implementers and reviewers of the full chain.
- [reporting-v1](reporting-v1.md) — Deterministic bug-bounty report generator (`sentinel report`, Markdown, JSON, or standalone HTML); for implementers and users rendering validated findings.
- [report-html-v1](report-html-v1.md) — Standalone HTML report export (`--format html`, self-contained, no JavaScript, no external resources, every value HTML-escaped); for implementers and users sharing a report as a single file.
- [report-csv-v1](report-csv-v1.md) — Flat CSV report export (`--format csv`, one row per finding plus a header row, RFC 4180 escaping, hostile values verbatim as inert text, formula injection is a spreadsheet-consumer risk); for implementers and users exporting findings to spreadsheets and triage tooling.
- [report-summary-v1](report-summary-v1.md) — Compact summary report format (`--format summary`, one-page plain-text executive summary: headline counts plus the top 10 findings, no `--generated-at`, empty set renders zero counts); for implementers and users briefing a report at a glance.
- [report-diff-v1](report-diff-v1.md) — Report diff between two runs (`sentinel report-diff <old.json> <new.json>`, added / removed / changed findings matched by finding_id, compared on severity / cvss_score / verdict / asset_id only, `merged_from` ignored as provenance, named shape errors, deterministic); for implementers and users seeing what changed after a re-run.
- [report-jsonl-v1](report-jsonl-v1.md) — Streaming JSONL report export (`--format jsonl`, one JSON object per line: a summary line first, then one finding per line in grouped order, each line the same shape as the JSON format's `findings` entries, no `--generated-at`, empty set renders the summary line only); for implementers and users feeding findings into a pipeline one line at a time.
- [report-validate-v1](report-validate-v1.md) — Report validation (`sentinel report validate <report.json> [--json]`, shape + per-finding strict check and rule verdict + report-id recomputation, exit 0 unless a structural error or band mismatch, report-id mismatch is a warning, read-only); for implementers and users checking a report file before trusting it.
- [report-merge-v1](report-merge-v1.md) — Report merge (`sentinel report merge <a-report.json> <b-report.json> [--out <merged.json>]`, identical findings kept once, disjoint unioned, same-id different content fails with REPORT_MERGE_CONFLICTING_FINDING, program must agree, merged report rendered by generateReport itself, summary line on stderr, stdout stays pure JSON); for implementers and users combining two runs, detectors, or targets into one report.
- [report-anonymize-v1](report-anonymize-v1.md) — Report anonymize for sharing (`sentinel report anonymize <report.json> [--out <anon.json>] [--salt <hex>]`, target/session/asset ids map to deterministic `anon-<sha256>` values, internal hostnames/IPs in `description` and evidence `notes` scrubbed, `asset_url` host scrubbed to a deterministic anon host (round 90; scheme/port/path/query/fragment preserved, userinfo stripped), report_id unchanged by design, `anonymized: true` metadata, passes `report validate`, salt never printed, de-identification not cryptographic redaction); for implementers and users sharing a report outside the lab.
- [report-split-v1](report-split-v1.md) — Report split into per-group reports (`sentinel report split <report.json> --by severity|verdict --out-dir <dir> [--force]`, one valid JSON report per non-empty severity or rule verdict, each with its own recomputed report id and a `split` metadata block, empty groups not written, --out-dir created mode 0700 and refused when non-empty without --force or inside the skill/state dir, stdout lists only the written paths, summaries on stderr); for implementers and users handing each severity or verdict group to a different team.
- [report-filter-v1](report-filter-v1.md) — Report filter into a threshold subset (`sentinel report filter <report.json> [--severity <level>] [--verdict <rule-verdict>] [--out <filtered.json>]`, at least one predicate required, both AND together, severity is a threshold matched case-insensitively, verdict is the rule verdict from `validateOneFinding` not the stored `validation_status` workflow state, empty result is a valid empty report, output rendered by `generateReport` itself with a `filter` metadata block, stdout pure JSON, summary on stderr); for implementers and users who want one report carrying only the findings that meet a threshold.
- [report-helpers-export-v1](report-helpers-export-v1.md) — Shared report-summary helpers exported (`executiveSummary` now exported from the generator alongside the already-exported `countBySeverity`; the filter empty report calls them instead of hand-replicating the wording, byte-identical output pinned by a golden, anti-divergence test, audit of the other report commands, `deriveExpectedReportId` deliberately left independent, `pickGeneratedAt` triple found and deferred); for implementers changing the generator's summary wording or counting.
- [report-generated-at-helper-v1](report-generated-at-helper-v1.md) — Shared `pickGeneratedAt` helper exported from the generator (newest valid `generated_at` among the source reports, else newest finding `created_at`, else null, never the wall clock; all four call sites — filter, split, merge, anonymize — refactored to it, each keeping its own named error on null; corrects round 72: the duplication was a quadruple, not a triple; byte-identical output pinned by 9 golden sha256, `generateReport`'s own fallback and `deriveExpectedReportId` deliberately left independent); for implementers changing how derived reports pick their timestamp.
- [report-stats-v1](report-stats-v1.md) — Report stats (`sentinel report stats <report.json> [--json]`, total + counts by severity / rule verdict / class + CVSS distribution + top 5 assets + executive summary line, exit 0 whenever the file parses, read-only, shape failures carry REPORT_DIFF_* codes); for implementers and users who want a quick triage answer without reading a whole report.
- [report-render-v1](report-render-v1.md) — Report render (`sentinel report render <report.json> --format markdown|json|html|csv|summary|jsonl [--out <file>]`, re-renders an existing JSON report through the generator's own render path, byte-identical to direct generation, source generated_at carried through, template sources refused, mixed-target sources render only when they declare mixed_targets); for implementers and users who already have a JSON report and want it in another format without re-running the pipeline.
