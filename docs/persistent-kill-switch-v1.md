# Persistent kill switch v2 (with v1 compatibility)

`src/policy/persistent-kill-switch.js` is a cross-process policy state controller for the local lab and future controlled wrapper. It is not a Muse-native API and it does not itself discover or kill arbitrary processes.

## State contract

- State lives at an explicit absolute path outside the installed skill directory, for example `~/workspace/sentinel-bounty/state/kill-switch.json`. The constructor requires both `stateFile` and `skillDirectory` and rejects paths inside the skill directory.
- Missing state means inactive; an active state is fail-closed for fresh processes.
- Writes use a temporary file, explicit mode `0600`, `chmod(0600)`, and atomic rename.
- A lock file serializes readers/writers and has bounded acquisition plus stale-lock recovery. The Muse lab separately verified that `flock` is available; this Node implementation avoids invoking a shell command for every state read.
- When the state lock cannot be acquired because storage is unavailable, `kill-switch status` falls back to a single canonical lockless read that reports the stored state without pruning and marks it `readMode: LOCKLESS_FALLBACK` (plus `lockless: true, pruned: false`) with each worker labelled `leaseExpired` and `registeredWorkers` counting live leases only. A live lock held by another process is intentionally not bypassed: a lockless read taken while the state is being written could return a stale pre-trigger snapshot, so `status` still fails with `KILL_SWITCH_STATE_LOCKED` in that case. Non-object worker entries in a hand-edited state file are dropped by both the lockless and locked paths, so the two snapshots report the same worker set. Lock-acquisition failures are classified, not lumped together: a live lock is `KILL_SWITCH_STATE_LOCKED`; a permission failure (`EACCES`/`EPERM`) is `KILL_SWITCH_STATE_PERMISSION_DENIED`; disk/quota exhaustion (`ENOSPC`/`EDQUOT`) is `KILL_SWITCH_STATE_UNAVAILABLE`; a non-directory path component (`ENOTDIR`) is `KILL_SWITCH_STATE_PATH_INVALID`; a stale lock is recovered and the operation proceeds. The audit log classifies its own lock the same way (`AUDIT_LOG_LOCKED`, `AUDIT_LOG_PERMISSION_DENIED`, `AUDIT_LOG_STORAGE_UNAVAILABLE`, `AUDIT_LOG_PATH_INVALID`), and `audit-health` reports those reasons before `reset` runs. Error messages carry only the code, never a token or digest value. The rotation lock (`rotate-token`/`revoke-token`) is classified the same way in its own namespace: a live lock is `RESET_TOKEN_ROTATION_LOCKED`; a permission failure is `RESET_TOKEN_ROTATION_PERMISSION_DENIED`; disk/quota exhaustion is `RESET_TOKEN_ROTATION_UNAVAILABLE`; a non-directory path component is `RESET_TOKEN_ROTATION_PATH_INVALID`; a stale rotation lock is recovered and the operation proceeds. Token-file writes are classified the same way, and a permission/path failure while reading the operator digest file is `RESET_TOKEN_FILE_PERMISSION_DENIED` / `RESET_TOKEN_FILE_PATH_INVALID` (a missing digest, an expired digest, or a wrong presented token still means no usable token, reported as `RESET_OPERATOR_UNAUTHORIZED`; a digest file that exists and is readable but holds no usable digest — unparseable JSON, wrong shape, or a legacy value that is not a 64-hex hash — is reported distinctly as `RESET_TOKEN_FILE_CORRUPT`, still fail-closed with exit 3, so the operator can tell "fix the file" apart from "wrong token"). State-file read failures are classified too: a permission failure is `KILL_SWITCH_STATE_PERMISSION_DENIED`, a non-directory path component is `KILL_SWITCH_STATE_PATH_INVALID`, and an unparseable or wrong-shape state file is `KILL_SWITCH_STATE_CORRUPT`; none of these carry a raw filesystem path.
- Approval state is intentionally not persisted by this controller. Reinstall/restart must not revive old approval IDs.
- The controller migrates legacy `{ "enabled": boolean, "reason": string }` and version-1 state shapes to version 2 while holding the state lock. `updatedAt` and `updated_at` are both accepted. Unknown or malformed shapes remain fail-closed errors. The v1/legacy migration lives in one shared pure function used by both the locked reader (which writes the migrated state back) and the lockless parser (in-memory only), so the two paths cannot drift apart.
- Worker registrations are persisted as short leases and renewed by the active wrapper. Reset reads leases under the state lock, so another process's live worker blocks reset. A reset requires a presented operator token plus an independently provisioned SHA-256 digest file; `resetBy` is audit context, not authentication. Status normally prunes leases under the lock, but on storage-unavailable lock acquisition it performs a read-only lockless fallback and marks expired workers rather than writing state; the fallback reports `readMode: LOCKLESS_FALLBACK` (plus `lockless: true, pruned: false`) and counts only live leases in `registeredWorkers`; a live lock still returns `KILL_SWITCH_STATE_LOCKED`.

The controlled wrapper polls this state while a child is active. A fresh controller can therefore activate the switch, and a wrapper in another process observes it and begins cancellation. The process-group cancellation path is strongest on POSIX runtimes; Windows uses the direct-child fallback.

The repository now exposes a local operator CLI: `kill-switch status`, `kill-switch trigger`, token-gated `kill-switch reset`, `kill-switch audit-health`, `kill-switch rotate-token`, and `kill-switch revoke-token`. The presented token is supplied through `SENTINEL_OPERATOR_RESET_TOKEN`, while the expected digest metadata is loaded from the independent file named by `SENTINEL_OPERATOR_RESET_TOKEN_HASH_FILE`; metadata carries `keyId` and ISO-8601 `validUntil` (default validity is approximately 90 days). Reset and rotation/revocation require a healthy audit path; trigger proceeds with an audit warning if logging fails. If reset is blocked by audit health, repair the regular JSONL audit file and verify with `audit-health` before retrying; do not disable the active state manually. Rotation requires `SENTINEL_OPERATOR_NEW_RESET_TOKEN`, atomically replaces the digest metadata, invalidates the old token immediately, and emits `KILL_SWITCH_TOKEN_ROTATED`. Revocation writes a pending marker, removes the digest, then writes `KILL_SWITCH_TOKEN_REVOKED`; completed markers are scoped by `keyId`, and retries recover a pending marker idempotently. `recovered: true` identifies reuse of a matching pending marker and does not imply that token authentication was skipped. If the digest is already missing, recovery of a valid pending marker may finalize the audit trail without token re-authentication; this does not grant reset access. Neither the token file nor `--actor` is a Muse-native identity or approval API. The local HTTP adapter uses the controller for lab-only cancellation.
